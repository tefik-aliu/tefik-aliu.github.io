01 / BEHAVIOUR

Who can change what?

The public demo stays open and uses sample data. Private installations require login when private mode is enabled. The API checks the session and role on each request.

A hidden button is not an access check. A viewer receives 403 even when attempting an update directly through the API.

02 / IMPLEMENTATION

Issue and history.
One transaction.

Each successful change records the actor, time and before/after state. If history cannot be written, the issue mutation rolls back too. Deleting an issue retains its history.

The interface shows changed fields and lets reviewers load older events. Existing issues receive no invented history when the database is upgraded.

03 / ENGINEERING CHOICES

Small, explicit boundaries.

Server-side sessions

Random session secrets, HttpOnly cookies and CSRF checks. Logout, password reset and role changes revoke sessions.

Local account provisioning

An administrator creates accounts through a CLI. No public registration or email password recovery.

SQLite and full snapshots

A shared transaction makes rollback explicit. Full snapshots cost storage but keep changes easy to inspect.

04 / VERIFICATION

Test the actions
that must be denied.

Tests cover anonymous requests, all three roles, CSRF, session expiry, logout, login throttling and database migration. A simulated storage failure verifies that issue and history writes roll back together.

Browser tests start isolated instances and exercise both modes, role-specific controls and mobile widths. They also run in GitHub Actions.

Boundaries

One workspace, without multi-tenancy, MFA or SSO. Private deployments require HTTPS and persistent storage. History is not tamper-proof against database administrators. Deleted issue content remains in history.
