Observability Lab

Ett API och en webbpanel där ett tappat nätverkssvar kan hanteras utan att samma jobb sparas två gånger. Databastransaktioner, uttryckliga återförsök och driftsignaler gör beteendet granskningsbart.

Arkitektur

Tjänstens delar

Problemet

Servern sparar ett jobb, men webbläsaren får aldrig svaret. Ett vanligt nytt försök kan då skapa en dubblett. Projektet låter klienten återhämta resultatet efter ett osäkert svar och visar mätvärden som hjälper till vid felsökning.

Implementationen

FastAPI sparar jobbet och ett kvitto på skapandet i samma databastransaktion. Med en valfri Idempotency-Key återfår klienten det ursprungliga svaret vid ett nytt försök; samma nyckel med en annan titel ger 409. PostgreSQL lagrar data i Compose, medan Prometheus, Grafana och valfri OTLP-spårning ger driftsignaler.

Designval

Säkra återförsök och tydliga felsignaler

En transaktion, ett kvitto

Ett unikhetsvillkor i databasen reserverar operationsnyckeln. Jobbet och kvittot sparas tillsammans; en misslyckad transaktion återställer båda. Samtidiga återförsök använder det sparade kvittot.

Granska implementationen ↗

Processhälsa och driftberedskap

/ready frågar databasen och ger 503 med ett stabilt meddelande när den är otillgänglig. /health fortsätter svara. Ett test verifierar fel, återhämtning och att privata databasdetaljer inte exponeras i svaret.

Granska implementationen ↗

Mätvärden med applikationskontext

Antal anrop och svarstider visas tillsammans med skapade jobb och jobb per status, vilket kopplar HTTP-beteende till tjänstens tillstånd.

Granska implementationen ↗

Ett medvetet nytt försök

Vid ett osäkert svar behåller formuläret titel och operationsnyckel och erbjuder Retry save. Webbläsartestet låter servern spara, tappar svaret och kontrollerar att återförsöket lämnar exakt ett sparat jobb.

def create_once(db: Session, title: str, key: str | None) -> tuple[dict, bool]:
    """Commit a job and its receipt together; the unique key arbitrates races."""
    receipt = JobRequest(key=key, title=title, response={}) if key else None
    try:
        if receipt is not None:
            db.add(receipt)
            db.flush()  # Reserve the key before creating the job.
        job = Job(title=title, status="queued")
        db.add(job)
        db.flush()
        body = JobRead.model_validate(job).model_dump(mode="json")
        if receipt is not None:
            receipt.response = body
        db.commit()
        return body, False
    except IntegrityError:
        db.rollback()
        existing = db.get(JobRequest, key) if key else None
        if existing is None:
            raise  # Do not misreport unrelated database failures as duplicates.
        if existing.title != title:
            raise HTTPException(409, "Idempotency-Key already used for a different title") from None
        return existing.response, True
    except Exception:
        db.rollback()
        raise

Exakt utdrag av create_once() från commit 18f6e6d. En unik nyckel avgör konkurrerande anrop i databasen. Återförsök returnerar det ursprungliga kvittot även efter att jobbet ändrats eller raderats.

Resultat och nästa steg

Integrationstester och begränsningar

Återförsöken är verifierade med SQLite, PostgreSQL och ett webbläsartest som simulerar ett tappat svar. Applikationen lagrar jobbtillstånd; den kör inga bakgrundsjobb och garanterar inte att effekter i externa system sker exakt en gång.

Webbläsarens nyckel finns i minnet och försvinner vid omladdning. Sparade kvitton saknar utgångstid och användaravgränsning. Autentisering, migreringar och gallring återstår. Collectorn använder en debug-exportör; den lokala stacken och Kubernetes-manifesten visar konfiguration utan dokumenterad produktionsdrift.
