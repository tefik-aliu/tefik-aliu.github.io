01 · The problem

Most portfolio APIs prove that an endpoint works. This project asks what happens next.

A service can return a successful response and still be difficult to operate. It may expose no readiness state, no useful metrics, no trace path, no deployment contract and no automated browser-level proof that the full workflow works.

Service Observability Lab was built to demonstrate a broader engineering question: Can a small service be understandable, testable and diagnosable before it becomes large?

Design principle
“Working locally” is the start of the evidence, not the end of it.

01

Application factory

create_app() accepts a database URL, making the service easy to start with PostgreSQL and easy to isolate with in-memory SQLite during tests.

02

Separate health and readiness

/health proves the process responds. /ready executes a database check so orchestration can distinguish alive from ready.

03

Useful metrics

Request count, latency, created jobs and jobs by status expose both technical behaviour and a small piece of business state.

04

Deployability as code

Docker Compose provides the full local stack. Kubernetes manifests define probes, resources, configuration and a provider-neutral service contract.

04 · Debugging record

The strongest evidence was not a perfect first run. It was the path from red to green.

The CI history records real integration problems and the changes used to resolve them.

  1. 01

    The workflow directory was missing

    The hidden .github folder was not included during the first repository upload. The workflow was recreated directly in the repository.

  2. 02

    Node cache expected a lockfile

    The browser job failed because npm caching was enabled without a compatible lockfile. The unnecessary cache configuration was removed.

  3. 03

    Static analysis exposed Python issues

    Ruff identified dependency-default and UTC-modernisation problems. The dependency wiring was refactored and timezone handling moved to datetime.now(UTC).

  4. 04

    Tests could not import the application package

    The CI command was changed to module-based invocation so the repository root remained on Python’s import path.

  5. ✓

    Both pipelines passed

    Python quality and browser QA completed successfully, leaving a visible, inspectable record of the debugging process.

05 · Honest limits

A credible case study states what the system does not prove.

Not production at scale

The repository demonstrates patterns and integration, not sustained traffic, multi-region resilience or a production SLO history.

No authentication layer

The lab focuses on service reliability and QA. Identity, permissions, audit logging and threat modelling remain future work.

Tracing uses a lab exporter

OpenTelemetry traces are sent to a collector with a debug exporter rather than a persistent tracing backend.

Kubernetes assets are provider-neutral

The manifests define probes, resources and configuration, but the project does not claim operation in a managed production cluster.

What I would build next

Turn visibility into operating decisions.

Add authentication, alert rules, SLO dashboards, persistent traces, database migrations, container image publishing and a staged deployment pipeline with rollback evidence.
