Architecture

Service components

The problem

The server saves a job, but the browser never receives the response. Repeating an ordinary creation request can save the same job twice. This project makes that uncertain outcome recoverable and exposes signals for diagnosing the service.

The implementation

FastAPI stores a job and its creation receipt in one database transaction. An optional Idempotency-Key lets a retry recover the original response; a different title with the same key returns 409. PostgreSQL stores state in Compose; Prometheus, Grafana and optional OTLP tracing provide operational signals.

Design decisions

Safe retries and useful failure signals

One transaction, one receipt

A database uniqueness constraint reserves the operation key. The job and receipt commit together; a failed transaction rolls both back. Concurrent retries reuse the saved receipt.

Health and readiness

/ready queries the database and returns 503 with a stable message when it is unavailable. /health still responds. A regression test verifies failure, recovery and that private database exception details stay out of the response.

Source excerpt

Recovering the original response

app/job_creation.py · L9–34 · 18f6e6dSource ↗ 
def create_once(db: Session, title: str, key: str | None) -> tuple[dict, bool]:
    """Commit a job and its receipt together; the unique key arbitrates races."""
    receipt = JobRequest(key=key, title=title, response={}) if key else None
    try:
        if receipt is not None:
            db.add(receipt)
            db.flush()  # Reserve the key before creating the job.
        job = Job(title=title, status="queued")
        db.add(job)
        db.flush()
        body = JobRead.model_validate(job).model_dump(mode="json")
        if receipt is not None:
            receipt.response = body
        db.commit()
        return body, False
    except IntegrityError:
        db.rollback()
        existing = db.get(JobRequest, key) if key else None
        if existing is None:
            raise  # Do not misreport unrelated database failures as duplicates.
        if existing.title != title:
            raise HTTPException(409, "Idempotency-Key already used for a different title") from None
        return existing.response, True
    except Exception:
        db.rollback()
        raise

Exact create_once() excerpt from commit 18f6e6d. A unique key arbitrates competing requests in the database. Replays return the original creation receipt, including after a job changes or is deleted.

Result & next steps

Integration tests and limitations

The retry contract is verified with SQLite, PostgreSQL and a browser simulation of a lost response. The application stores job states; it does not execute background jobs or guarantee exactly-once effects in external systems.

Browser keys are kept in memory and are lost on reload. Stored receipts have no expiry or user scope. Authentication, migrations and retention policy remain extensions. The collector uses a debug exporter; the local stack and Kubernetes manifests demonstrate configuration, without a production operating history.
