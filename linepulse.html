01 / ARCHITECTURE

One event.
Several useful outputs.

The problem

Raw events do not explain why output changes. A useful system needs to connect downtime, defects and process conditions to measurements an operator can inspect.

The implementation

The browser advances the simulator through an API. Events are stored through SQLAlchemy, then analysed for OEE, reliability indicators and alert conditions. The same dataset feeds an Excel shift report.

Each alert includes the measured condition, its trigger and a suggested next action.

02 / ENGINEERING DECISIONS

Small enough to run.
Structured enough to inspect.

An explicit database boundary

SQLite keeps the demo easy to run. SQLAlchemy and DATABASE_URL isolate persistence configuration; PostgreSQL is a deployment target, not a claim about the live demo.

Inspect implementation ↗

Explainable rules

Pressure drift and clustered stops are evaluated with explicit conditions. Alerts expose their evidence instead of assigning opaque confidence scores.

Inspect implementation ↗

Failure is part of the model

A dependency-failure scenario makes readiness return HTTP 503. Liveness remains a separate process check.

Inspect implementation ↗

Reporting shares the data model

The XLSX export derives from stored events and the same analysis boundary used by the dashboard.

03 / VERIFICATION

Test the behaviour.
Keep the evidence.

Checks at different boundaries

  • Analytics tests check bounded KPIs and scenario-specific alerts.
  • API tests exercise endpoint behaviour and service state.
  • Playwright checks the dashboard in Chromium.
  • CI runs Python checks separately from TypeScript and browser QA.
